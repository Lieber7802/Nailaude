# nailaude 技术文档

## 1. 技术定位

nailaude 是一个 IM 式多智能体协作系统。它不是把多个模型简单排列在聊天窗口里，而是围绕“会话”建立一套共享上下文、任务调度和产物反馈机制，让不同智能体能够在同一个项目空间中连续协作。

系统中有两类角色：

| 角色 | 职责 |
|---|---|
| 主智能体 Orchestrator | 理解用户意图、拆解任务、选择智能体、维护协作状态 |
| 子智能体 Agent | 根据任务完成需求分析、代码实现、代码审查、文档编写等具体工作 |

Orchestrator 不直接替代子智能体执行专业任务。它的核心职责是“组织协作”：把用户请求转成可执行任务链，将任务交接给合适的智能体，并把执行结果重新沉淀回会话上下文。

## 2. 总体架构

```text
用户
  |
  | REST / WebSocket
  v
前端工作台
  |
  | 会话、消息、@ 提及、协作状态、预览面板
  v
FastAPI 后端
  |
  |-- Conversation / Message / Agent API
  |-- WebSocket 运行通道
  |-- Orchestrator：规划、校验、调度、运行
  |-- Team Protocol：团队共享状态
  |-- Project State：项目事实摘要
  |-- Artifact / Preview：产物与预览
  v
Agent Adapter 层
  |
  |-- OpenCode / Codex / LLM Provider / Mock
  v
会话工作目录与智能体产物
```

前端负责把多智能体协作过程可视化：聊天流、任务状态、产物卡片和右侧预览。后端负责会话持久化、任务规划、Agent 调用、共享状态维护和产物生成。

## 3. 核心数据模型

| 模型 | 作用 |
|---|---|
| `Agent` | 用户可见的智能体角色，包含能力标签、头像、系统指令和平台绑定 |
| `Conversation` | 一个协作空间，绑定参与智能体、工作目录和消息历史 |
| `Message` | 用户、智能体、主智能体和团队活动的消息记录 |
| `Artifact` | 智能体产出的代码、网页、Diff、文档和日志 |
| `TeamBoard` | 会话级共享面板，保存团队决策、规范、问题和进度 |
| `TeamNote` | 智能体之间传递的原子协作信息 |
| `ProjectState` | 工作目录的文件树、Git 状态、近期变更和项目摘要 |
| `OrchestratorRun` | 一次主智能体运行的完整状态快照 |

这些模型共同保证：多个智能体不是各自完成孤立回复，而是在同一个会话状态中共享任务边界、项目进度、前序结果和产物记录。

## 4. 会话共享上下文分层

nailaude 的协作上下文按用途分层。主智能体规划任务时只读取摘要层信息，子智能体执行任务时再获得更具体的任务交接信息。

```text
Layer 0 用户意图
  用户原始请求、@ 提及、澄清回答

Layer 1 参与者
  当前会话智能体、能力标签、角色说明

Layer 2 项目状态
  工作目录、文件树、Git 状态、近期变更、项目摘要

Layer 3 团队协作
  Team Board、Team Notes、团队决策、代码规范、开放问题

Layer 4 任务交接
  当前任务、验收标准、依赖结果、导航建议、上下文预算
```

### 4.1 PlannerContext

PlannerContext 是主智能体规划任务时使用的上下文。它由用户请求、mentions、本轮可分派智能体、项目摘要、团队共享状态、最近对话和文件树摘要组成。

它的设计目标是“足够规划，但不过量注入”。Planner 不读取完整源码，只负责判断任务应该如何拆、交给谁、按什么依赖顺序执行。具体文件探索和实现交给后续子智能体完成。

显式 `@` 是本轮任务边界：

- 用户明确 @ 某些智能体时，本轮 Planner 只在这些智能体中分配任务。
- 用户没有 @ 时，默认使用会话内全部参与智能体。

这样可以避免主智能体调用用户没有选择的角色，同时保留自动分配能力。

### 4.2 子任务交接上下文

子智能体执行前会收到一个结构化交接包。它不会只收到一句用户原话，而是会看到：

- 当前任务目标和验收标准。
- 当前工作目录和快照。
- 项目摘要。
- 相关团队规范和便签。
- 前序任务结果。
- 建议优先查看的文件或变更摘要。

这让产品架构师的需求分析可以传递给代码工匠，代码工匠的变更可以传递给审查大师，审查结论也可以继续影响文档专家。

## 5. 多智能体协作运行流程

```text
用户发送消息
  |
  v
解析 @ 与本轮参与智能体
  |
  v
构建共享上下文
  |
  v
Planner 生成任务计划
  |
  v
Validator 校验计划
  |
  v
Scheduler 按依赖生成批次
  |
  v
Runtime 调用子智能体执行
  |
  |-- 收集文本回复
  |-- 收集文件变化
  |-- 收集团队便签
  |-- 生成产物卡片
  |-- 刷新 Team Board / Project State
  v
WebSocket 推送状态与产物
```

一次复杂任务通常会被拆成多个阶段。例如：

```text
需求分析 -> 代码实现 -> 代码审查 -> README 文档
```

这些阶段之间通过依赖关系连接。某个任务失败后，依赖它的后续任务会被标记为 `blocked`，用户可以在协作状态卡片中看到失败和阻塞来源。

## 6. 任务计划、校验与执行

Planner 输出的是结构化任务计划，而不是自由文本。一个任务会包含负责人、目标、指令、验收标准和依赖关系。

后端会对计划做确定性校验：

- 任务数量不能过大。
- task id 必须唯一。
- agent 必须来自当前参与者。
- 依赖必须指向已知任务。
- 依赖图不能成环。

校验通过后，Scheduler 根据依赖关系生成执行批次；Runtime 负责执行批次、更新任务状态、捕获文件变化，并把最新完整状态通过 WebSocket 推给前端。

Runtime 中常见状态包括：

| 状态 | 含义 |
|---|---|
| `pending` | 等待执行 |
| `running` | 正在执行 |
| `completed` | 已完成 |
| `failed` | 执行失败 |
| `blocked` | 前序任务失败，当前任务无法继续 |
| `cancelled` | 用户终止或系统取消 |

这部分设计让 AI 协作过程从“不可见的长等待”变成“可观察的任务流”。

## 7. Team Board 与 Project State

Team Board 和 Project State 是 nailaude 让智能体共享上下文的两个核心状态。

### 7.1 Team Board

Team Board 保存会话级团队共识，关注“协作中形成了什么约定”：

- 当前参与智能体。
- 团队决策。
- 代码规范。
- 开放问题。
- 当前任务进度。
- 最近智能体便签。

智能体在执行任务时可以产生 Team Note，例如提醒、问题、决策或规范。系统会在一个批次结束后统一合并这些 notes，避免并行任务直接互相覆盖共享状态。

### 7.2 Project State

Project State 保存工作目录的事实摘要，关注“项目现在是什么状态”：

- 工作目录与文件树。
- 技术栈线索。
- Git 分支、HEAD、dirty 状态。
- 最近文件变更。
- 项目进度摘要。

Project State 不保存完整源码，也不替代 Git。它给主智能体和子智能体提供项目态势，让任务规划和后续交接不必完全依赖聊天历史。

### 7.3 两者如何配合

Team Board 更像团队白板，记录决策和协作约定；Project State 更像项目快照，记录文件和进度事实。每个批次结束后，系统会根据任务结果同时刷新两者，再把新版本推送给前端。

## 8. 产物与预览闭环

智能体输出文件事件后，系统会将其转成 Artifact：

```text
file_created / file_modified
  |
  v
ArtifactService
  |
  |-- 写入工作目录
  |-- 推断产物类型
  |-- 生成 previewUrl 或 diffData
  v
WebSocket artifact event
  |
  v
前端产物卡片 + 右侧预览面板
```

预览系统支持：

| 产物 | 展示方式 |
|---|---|
| HTML 页面 | iframe 预览 |
| Vite 项目 | 后端按需启动 dev server 并代理 |
| Markdown 文档 | 右侧文档预览 |
| 代码文件 | 代码查看 |
| 文件修改 | Diff 视图 |

这让多智能体协作形成闭环：用户提出任务，智能体生成产物，系统展示预览和变更，用户继续基于结果迭代。

## 9. 前后端同步

nailaude 使用 WebSocket 承载主要运行流。后端会推送：

- 用户消息持久化结果。
- 智能体开始思考。
- 智能体文本流。
- 产物事件。
- 团队活动。
- 主智能体状态快照。
- Team Board / Project State 更新。
- 错误信息。

其中 `orchestrator_status` 是完整快照，包含 run 状态、任务列表、批次、warning 和共享状态版本。前端不需要自行推断复杂运行状态，只负责展示后端权威状态。

## 10. 可靠性与边界控制

| 风险 | 控制方式 |
|---|---|
| Planner 输出不稳定 | schema 解析、确定性校验和一次 replan |
| 模型编造 agent | agent 必须来自当前参与者和 catalog |
| 未 @ 智能体被误调用 | 显式 @ 时收窄本轮可分派智能体 |
| 任务依赖错误 | DAG 校验和环检测 |
| 子任务失败 | 后续依赖任务标记为 blocked |
| 用户中止 | cancel event 覆盖队列、规划和执行阶段 |
| 共享状态冲突 | Team Notes 在批次结束后统一合并 |
| 上下文过大 | 子任务交接包按预算压缩 |
| 文件路径逃逸 | 工作目录路径解析和相对路径校验 |
| 预览资源丢失 | HTML 路径重写和 Vite proxy |

系统还保留 Mock Adapter，保证核心协作链路在没有外部模型或 CLI 的情况下也能验证和演示。

## 11. 启动方式

后端：

```bash
cd backend
.venv/bin/python -m uvicorn app.main:app --reload --port 8000
```

前端：

```bash
cd frontend
npm run dev
```

默认地址：

```text
前端：http://localhost:5173
后端：http://127.0.0.1:8000
WebSocket：ws://127.0.0.1:8000/ws/{conversation_id}
Preview：http://127.0.0.1:8000/preview/{conversation_id}/*
```
