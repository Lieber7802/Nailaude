# AgentHub 多 Agent 协作平台：课题原稿与理解说明

## 一、课题原稿整理

# AgentHub - 多 Agent 协作平台设计

## 课题：AgentHub - 多 Agent 协作平台

## 课题背景

通过对话式交互创建网页、Workflow 等产物。本课题要求学生构建一个该业务的简化实战版：**多 Agent 协作平台（AgentHub）**。

平台采用 **IM 聊天作为核心交互范式**。用户像使用飞书 / 微信一样，通过新建对话、发送消息的方式与不同 AI Agent 进行交互。每个 Agent 就是一个“聊天对象”，用户可以：

- **新建对话**：创建一个新的聊天会话，选择或指定要对话的 Agent，例如 Claude Code、Codex、OpenCode 等。
- **多会话并行**：同时开启多个对话窗口，分别与不同 Agent 交流不同任务，类似 IM 的多个聊天窗口。
- **群聊协作**：在一个对话中 @ 多个 Agent，由主 Agent（Orchestrator）自动调分工，多个 Agent 像群聊成员一样依次回复各自的产出。
- **上下文连续**：每个对话保持完整的聊天历史，Agent 能基于历史消息理解上下文，支持多轮迭代修改。
- **产物内联**：Agent 的回复不仅是文字，还可以内联展示代码 Diff、网页预览卡片、文件附件等富媒体产物，用户可直接在聊天流中预览和操作。

平台同时接入市面主流 Agent 平台（Claude Code、Codex、OpenCode 等），通过统一适配器层屏蔽 API 差异，并支持用户自建 Agent。

所有 Agent 产出（代码、网页、文档、PPT 等）支持实时预览、代码二次编辑和一键部署发布。

---

## 核心功能

## 1. IM 聊天式交互（核心体验）

| 功能 | 说明 |
|---|---|
| 对话列表 | 左侧会话列表，支持新建 / 置顶 / 归档 / 搜索，按最近活跃排序 |
| 单聊模式 | 1v1 与单个 Agent 对话，适合明确任务，例如“用 Claude Code 写一个 React 组件” |
| 群聊模式 | 一个对话中包含多个 Agent，通过 @ 指定由 Orchestrator 自动分派，Agent 依次回复 |
| 消息类型 | 文本、代码块、图片、文件附件、网页预览卡片、Diff 视图卡片、部署状态卡片等 |
| 消息操作 | 回复、引用、重新生成、复制代码、一键应用 Diff、展开预览 |
| 上下文管理 | 聊天历史自动作为上下文传递给 Agent，支持手动 pin 关键消息作为长期上下文 |

---

## 2. 主 Agent 协调器（Orchestrator）

- 在群聊模式下，自动理解用户意图，将复杂任务拆解并分派给合适的子 Agent。
- 子 Agent 完成后，Orchestrator 聚合产出并在聊天流中汇报结果。
- 支持并行调度、失败降级、代码冲突处理。

---

## 3. 多 Agent 接入

- 统一适配器层，至少接入 2 个主流 Agent 平台，例如 Claude Code + Codex / OpenCode。
- 支持用户自建 Agent，对话式创建，设定 System Prompt + 工具集。
- 每个 Agent 在聊天列表中显示为独立“联系人”，有头像、名称、能力标签。

---

## 4. 产物预览与编辑

- Agent 回复中内联产物卡片，例如网页 iframe、文档渲染、PPT 浏览等。
- 点击卡片可展开全屏预览 / 代码编辑器。
- 支持 Diff 视图、版本历史、对话式局部修改，例如选中代码后在聊天中描述修改。

---

## 【P2】5. 部署发布

- 聊天中直接发送“部署”指令，Agent 返回部署状态卡片。
- 支持一键生成预览 URL / 静态站点部署 / 容器化部署 / 源码打包下载。

---

## 【P2】6. 多端支持

|---|---|
| Web 端 | 主力端，完整 IM 体验 + 代码编辑 + 全功能 |
| 桌面端 | 本地文件访问、系统通知、Agent 进程管理 |
| 移动端 | 轻量 IM 体验，查看对话、审批确认、产物预览 |

# 二、课题理解与功能解释

## 1. 课题核心定位

本课题要求构建一个简化实战版的 **多 Agent 协作平台 AgentHub**。

它的核心不是从零实现一个全新的底层 Agent，也不是复刻 Claude Code、Codex 或 OpenCode，而是做一个类似飞书 / 微信 / Slack 的 **IM 聊天式 Agent 工作台**。

用户可以像和联系人聊天一样，与不同 AI Agent 进行交互；也可以在一个群聊中同时 @ 多个 Agent，由主 Agent 或 Orchestrator 进行任务拆解、分派和结果汇总。

一句话理解：

> AgentHub 是一个把多个 Agent 接入到统一聊天界面中，并支持多 Agent 协作、产物预览、代码 Diff 和部署发布的 AI 工作台。

---

## 2. 这个课题不是做什么？

为了避免方向跑偏，需要先明确几个边界。

### 2.1 不是自研 Claude Code

课题中提到 Claude Code、Codex、OpenCode 等，是希望平台可以接入这些主流 Agent，而不是要求学生自己从零实现一个同等级别的 Coding Agent。

所以重点不是：

> 自研一个最强代码生成 Agent。

而是：

> 设计一个平台，把不同 Agent 统一接入、统一展示、统一调度。

---

### 2.2 不是普通多模型聊天窗口

如果只是做一个类似 ChatGPT 聚合站，让用户选择不同模型聊天，这个是不够的。

本课题强调：

- 多 Agent 协作；
- 任务拆解；
- 代码 Diff；
- 网页预览；
- 文件 / 文档 / PPT 等产物展示；
- 部署发布；
- AI 协作 Spec / Skill / Rule 沉淀。

所以它应该比普通聊天应用更偏“AI 工作台”。

---

### 2.3 不是纯后端 Workflow 系统

虽然项目里有 Orchestrator 和 Workflow 的概念，但课题非常强调 **IM 聊天式交互体验**。

因此，用户应该主要通过聊天窗口和 Agent 交互，而不是只在后台配置一个流程图。

---

## 3. 课题重点是什么？

根据原课题描述和考察要点，这个项目的重点主要有五个。

## 3.1 IM 聊天式交互

平台的核心交互方式是聊天。

用户可以：

- 新建对话；
- 选择一个 Agent 进行单聊；
- 同时打开多个会话；
- 在一个会话中 @ 多个 Agent；
- 查看完整聊天历史；
- 将历史消息作为上下文继续对话；
- 在聊天流中查看代码、网页、文件、Diff、部署状态等产物。

这里的 Agent 可以理解成一个“聊天对象”或“AI 联系人”。

---

## 3.2 多 Agent 协作

课题希望支持多个 Agent 在同一个任务中协作。

例如用户说：

```text
帮我生成一个 React 页面，并检查代码质量。
````

平台可以让 Orchestrator 自动分派：

```text
@ClaudeCode 负责生成页面代码
@Codex 负责审查代码
@OpenCode 负责运行或部署检查
```

多个 Agent 的输出应该能够在同一个聊天流中展示，并最终由 Orchestrator 汇总。

这里的重点是：

> 多 Agent 不是简单并排回复，而是要体现任务分工、调度和结果聚合。

---

## 3.3 多 Agent 接入

平台需要接入多个主流 Agent 平台，例如：

* Claude Code
* Codex
* OpenCode
* 用户自定义 Agent

这里建议设计一个统一的 Agent Adapter 层，用来屏蔽不同 Agent 的 API 差异。

每个 Agent 在平台中应当有：

* 名称；
* 头像；
* 能力标签；
* System Prompt；
* 工具集配置；
* 调用方式。

可以把每个 Agent 抽象成统一接口：

```ts
interface AgentProvider {
  id: string;
  name: string;
  capabilities: string[];
  sendMessage(input: AgentInput): Promise<AgentOutput>;
}
```

这样平台上层不用关心底层到底是 Claude Code、Codex 还是自定义 Agent。

---

## 3.4 产物预览与编辑

Agent 的回复不应该只是一段文本。

课题中明确提到，Agent 的产出可以包括：

* 代码；
* 网页；
* 文档；
* PPT；
* 文件附件；
* Diff；
* 部署状态。

因此，聊天流中需要支持不同类型的“产物卡片”。

例如：

| 产物类型 | 展示方式               |
| ---- | ------------------ |
| 代码   | 代码块 / 代码编辑器        |
| 网页   | iframe 预览卡片        |
| Diff | Diff 视图卡片          |
| 文档   | Markdown / 文档渲染    |
| PPT  | PPT 浏览卡片，可作为 P2 功能 |
| 文件   | 附件卡片               |
| 部署   | 部署状态卡片             |

这个功能是区分普通聊天产品和 AgentHub 的关键。

---

## 3.5 部署发布

课题中提到“部署发布”，但它属于偏后期或 P2 能力。

在 MVP 阶段，不一定要做复杂的云部署，可以先做简化版：

```text
Agent 生成网页代码
→ 平台保存到 workspace
→ 启动本地预览服务
→ 返回预览 URL
→ 在聊天中展示部署状态卡片
```

或者更简单：

```text
Agent 生成静态 HTML
→ 平台生成静态文件
→ iframe 直接预览
```

关键是要形成一个“生成 → 预览 → 发布/交付”的闭环。

## 4. 对几个模糊概念的解释

## 4.1 “AgentHub”到底是什么？

AgentHub 可以理解成：

> 多个 AI Agent 的统一入口和协作工作台。

它不是某一个 Agent，而是一个平台。

平台负责：

* 管理 Agent；
* 管理会话；
* 转发用户消息；
* 组织多 Agent 协作；
* 展示 Agent 产物；
* 管理上下文；
* 处理代码 Diff、网页预览和部署状态。

---

## 4.2 “每个 Agent 是一个聊天对象”是什么意思？

意思是：用户不需要理解复杂的 API 或命令行工具，而是像聊天一样使用 Agent。

例如：

```text
Claude Code：擅长代码生成
Codex：擅长代码审查
OpenCode：擅长项目运行和部署
PRD Agent：用户自定义，擅长需求文档
```

这些 Agent 都显示在联系人列表中，用户可以选择单聊，也可以在群聊中 @ 它们。

---

## 4.3 “群聊协作”是什么意思？

群聊协作不是普通多人聊天，而是多个 Agent 围绕同一个任务协作。

例如：

```text
用户：帮我设计一个登录页，并生成代码和预览效果。

Orchestrator：我将任务拆成三部分：
1. UI Agent 负责页面设计；
2. Code Agent 负责生成 React 代码；
3. Reviewer Agent 负责检查代码质量。
```

然后每个 Agent 依次输出结果，最后由 Orchestrator 汇总。

---

## 4.4 “Orchestrator”是什么？

Orchestrator 可以理解成“主 Agent 协调器”。

它负责：

* 理解用户意图；
* 判断需要哪些 Agent；
* 拆分任务；
* 分派任务；
* 汇总多个 Agent 的输出；
* 处理失败或冲突。

MVP 阶段不需要做得特别复杂，可以先采用规则 + LLM 的方式。

例如：

```text
如果用户 @ 了某个 Agent，就直接调用该 Agent；
如果用户提到“审查代码”，就调用 Reviewer Agent；
如果用户提到“部署”，就调用 Deploy Agent；
如果用户没有指定 Agent，就由 Orchestrator 根据能力标签选择。
```

---

## 4.5 “上下文连续”是什么意思？

上下文连续指的是：

> 每个对话应该保留完整聊天历史，Agent 能够基于历史消息理解当前任务。

例如用户先让 Agent 生成一个页面，之后又说：

```text
把刚才那个按钮改成蓝色。
```

Agent 应该知道“刚才那个按钮”指的是前面生成页面中的按钮。

MVP 中可以采用简单策略：

```text
当前用户消息
+ 最近若干轮聊天历史
+ 用户手动 pin 的关键消息
+ 当前产物摘要
```

不一定要一开始就做复杂的上下文压缩算法。

---

## 4.6 “Skill / Rule / Spec”是什么？

课题评分中提到 AI 协作能力，包括沉淀 Spec、Skill、Rule 等协作规范。

可以这样理解：

### Spec

Spec 是协作规范或任务说明，例如：

```text
代码生成 Agent 输出必须包含文件路径、代码内容和说明。
```

### Skill

Skill 是可复用的能力包，例如：

```text
Code Review Skill：当有代码产物生成后，自动让 Reviewer Agent 检查代码质量。
```

### Rule

Rule 是触发规则，例如：

```text
如果消息中包含“部署”，则触发 Deploy Agent。
如果代码产物生成完成，则触发 Diff 展示。
如果用户 @ 多个 Agent，则进入群聊协作模式。
```

MVP 阶段可以把 Skill / Rule 做成配置化能力，不需要做复杂插件系统。

## 5. 推荐的项目理解

更准确的项目理解是：

> AgentHub 是一个 IM 式多 Agent 协作平台。它通过统一 Agent Adapter 接入 Claude Code、Codex、OpenCode 等外部 Agent，通过 Orchestrator 实现群聊中的任务分派和结果汇总，通过产物卡片展示代码、网页、文档、Diff 和部署状态，从而让用户像使用聊天工具一样完成 AI 协作开发和内容生成。

## 7. 项目中 Harness 能力的正确位置

虽然这个课题不是主打自研底层 Harness，但仍然可以保留轻量 Harness 能力。

这里的 Harness 应该服务于 AgentHub 的产品主线，包括：

* Agent Adapter：统一接入不同 Agent；
* Orchestrator：负责多 Agent 调度；
* Context Manager：管理对话上下文；
* Skill / Rule Registry：沉淀协作规则；
* Artifact Router：把 Agent 输出转成可展示产物；
* Tool Executor：执行预览、Diff、部署等平台动作。

需要注意：

> Harness 是支撑层，不是项目主线。主线仍然是 IM 交互、多 Agent 协作和产物展示。
