# AgentHub 多 Agent 协作平台 - 产品需求文档 (PRD)

> 版本：v1.6 | 更新日期：2026-05-21 | 目标：20 天比赛 MVP

---

## 一、产品定位

**一句话定位：**

> AgentHub 是一个以 IM 聊天为核心交互的多 Agent 协作工作台，让用户像使用飞书一样与多个 AI Agent 对话、协作、生成和预览产物。

**核心价值主张：**

- 统一入口：多个 Agent（代码生成、代码审查、文档撰写等）集中在一个聊天界面
- 协作能力：支持群聊中多 Agent 协作完成复杂任务
- 产物可视化：Agent 输出不仅是文字，而是可交互的产物卡片（代码、网页预览、Diff）
- 即时预览：生成的网页/代码可在平台内实时预览，所见即所得

**与竞品的差异：**

| 对比维度 | 普通 AI 聊天 | AgentHub |
|---------|------------|----------|
| Agent 数量 | 单一模型切换 | 多 Agent 多平台协作 |
| 交互方式 | 纯文本问答 | IM 式 + 产物卡片 |
| 产物展示 | Markdown 渲染 | iframe 实时预览 + Diff 视图 |
| 协作模式 | 无 | Orchestrator 自动分派 |
| 平台接入 | 单一后端 | 多平台适配器统一接入 |

## 二、用户角色

| 角色 | 描述 | 核心诉求 |
|------|------|---------|
| 开发者用户 | 比赛评委 / 使用平台进行 AI 协作开发的人 | 通过自然语言与 Agent 对话，快速生成代码/网页，预览效果，迭代修改 |
| 平台管理员 | 配置 Agent、管理系统的角色（MVP 阶段即开发者本人） | 接入新 Agent、配置 Persona、管理系统设置 |

> MVP 阶段只聚焦「开发者用户」角色，管理后台以配置文件 / 简单设置页代替。

## 三、核心场景

### 场景 1：单聊生成网页（Demo 核心路径）

```
用户 → 新建对话 → 选择 "代码工匠" → 指定项目目录 ~/my-project
用户：帮我生成一个简洁的登录页面
代码工匠：好的，我来为你生成...（在项目目录中创建文件）
[代码卡片：~/my-project/login.html + login.css]
[网页预览卡片：iframe 实时渲染]
用户：把按钮改成圆角蓝色
代码工匠：已修改...（修改项目目录中的文件）
[Diff 卡片：显示文件变更]
[网页预览卡片：更新后效果]
```

### 场景 2：群聊多 Agent 协作（跨平台协作）

```
用户 → 新建群聊 → 添加 代码工匠 + 审查大师 → 指定项目目录
用户：@代码工匠 帮我生成一个 Todo List 页面，@审查大师 检查代码质量
Orchestrator：收到，分派任务中...
  → 代码工匠 负责生成代码
  → 审查大师 负责代码审查
代码工匠：（在项目目录中生成文件）[代码卡片] [网页预览卡片]
审查大师：（读取项目文件，审查代码）[审查报告] [修改建议 Diff]
Orchestrator：任务完成，汇总如下...
```

### 场景 3：多轮迭代修改

```
用户：（在已有对话中）把导航栏改成固定顶部
Agent：（基于上下文理解"导航栏"指代）
[Diff 卡片：position: fixed 修改]
[网页预览卡片：更新效果]
```

### 场景 4：自定义 Agent

```
用户 → Agent 管理 → 创建新 Agent 角色
设置名称：产品经理
设置能力描述：擅长将用户需求整理成结构化的 PRD 文档
设置能力标签：[产品, 文档, 需求分析]
（底层自动绑定到默认平台实例）
用户 → 与"产品经理"对话 → 指定项目目录
用户：帮我写一个社交 App 的需求文档
产品经理：（在项目目录中生成 PRD.md）[文档卡片]
```

## 四、多平台 Agent 接入方案

> **课题硬性要求：至少接入 2 个主流 Agent 平台。**
>
> **核心设计理念：我们不自研子 Agent 的 Harness（工具调用、代码执行、文件操作等），而是直接接入已有的第三方 Agent 平台实例。这些平台本身就是完整的 Coding Agent，自带代码生成、文件操作、命令执行等全套能力。AgentHub 只做统一入口、调度和产物展示。**

### 4.1 接入架构

```
┌──────────────────────────────────────────────────────────────────┐
│                      AgentHub 平台层                               │
│                                                                  │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │              统一 Agent Adapter 接口                         │  │
│  │   interface AgentAdapter {                                  │  │
│  │     platform: "opencode" | "codex"                          │  │
│  │     startSession(workDir): Session                          │  │
│  │     sendMessage(session, message): AsyncStream<AgentEvent>  │  │
│  │     stopSession(session): void                              │  │
│  │   }                                                         │  │
│  └──────────────────┬────────────────────┬────────────────────┘  │
│                     │                    │                        │
│  ┌──────────────────▼──────┐  ┌─────────▼──────────────────┐    │
│  │    OpenCode Adapter     │  │     Codex Adapter          │    │
│  │                         │  │                             │    │
│  │  - 开源 Go CLI          │  │  - OpenAI 开源 Coding Agent │    │
│  │  - 支持 75+ 模型后端     │  │  - 支持 full-auto 模式      │    │
│  │  - 可接入 DeepSeek 模型   │  │  - 支持 Responses API       │    │
│  │  - 有会话管理能力        │  │  - 内置代码执行沙箱         │    │
│  │  - MCP 协议支持         │  │  - 支持文件读写             │    │
│  │                         │  │                             │    │
│  │  接入方式：              │  │  接入方式：                  │    │
│  │  CLI 子进程 / API 调用   │  │  CLI 子进程 (full-auto模式) │    │
│  └─────────────────────────┘  └─────────────────────────────┘    │
│                                                                  │
│  Agent 实例运行模式：                                              │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │  模式A：服务器托管（本机预启动 Agent 进程）                   │    │
│  │  模式B：用户本地（用户自行安装 Agent CLI，平台远程连接）       │    │
│  └──────────────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────────────┘
```

### 4.2 平台选型与接入方式

| 平台 | 优先级 | 特点 | 接入方式 | 模型后端 |
|------|--------|------|---------|---------|
| **OpenCode** | P0 | 开源 MIT、支持 75+ 模型、MCP 协议、会话管理 | CLI 子进程 / HTTP API | **DeepSeek API**（比赛私有 Key，OpenAI 兼容） |
| **Codex CLI** | P0 | OpenAI 官方、full-auto 模式、内置沙箱执行 | CLI 子进程 (quiet模式) | OpenAI API / DeepSeek fallback |
| 自定义 Agent | P1 | 用户配置任意 Agent 实例连接 | 配置化接入 | 用户自选 |

### 4.3 Agent 平台能力对比

| 能力 | OpenCode | Codex CLI |
|------|----------|-----------|
| 代码生成 | ✅ | ✅ |
| 文件读写 | ✅ | ✅ |
| 命令执行 | ✅ | ✅ (沙箱内) |
| 多轮对话 | ✅ (会话管理) | ✅ |
| 流式输出 | ✅ | ✅ |
| 工具调用 | ✅ (MCP) | ✅ (内置工具) |
| 模型灵活性 | 高（75+ provider） | 低（仅 OpenAI） |
| 开源 | ✅ MIT | ✅ Apache 2.0 |
| 安装成本 | Go 二进制 | Node.js CLI |

### 4.4 两种运行模式

#### 模式 A：服务器托管（MVP 默认模式）

```
用户浏览器 → AgentHub 后端 → 本机上运行的 Agent 进程
                                ├── OpenCode 实例 (DeepSeek 模型后端)
                                └── Codex 实例 (OpenAI 模型 / DeepSeek fallback)
```

- 后端自动管理 Agent 进程的生命周期（启动/停止/重启）
- 用户无需本地安装任何 Agent CLI
- 适合 Demo 演示和评委体验

#### 模式 B：用户本地 Agent

```
用户浏览器 → AgentHub 后端 → 用户本机已安装的 Agent CLI
                              (通过配置的连接方式通信)
```

- 用户自行安装 OpenCode / Codex CLI
- 在设置中配置 Agent 实例地址/路径
- 适合开发者日常使用场景

### 4.5 工作目录管理

**用户指定项目目录**：用户在创建会话时指定（或选择）一个本地项目目录，Agent 实例在该目录内工作。

```
创建新对话时：
┌──────────────────────────────────┐
│  项目目录：[浏览...] /home/user/my-project
│  选择 Agent：OpenCode / Codex
└──────────────────────────────────┘
```

- Agent 的所有文件操作（生成代码、修改文件等）都发生在用户指定的目录中
- 平台捕获 Agent 对该目录的文件变更，生成 Diff 卡片
- 生成的网页文件可直接在该目录启动预览服务

### 4.6 用户层与平台层分离（关键产品设计）

> **设计原则：用户只与"Agent 角色"交互，完全不需要知道底层用了什么平台。**

```
┌─────────────────────────────────────────────────────────────┐
│  用户看到的（User-facing Agent 角色）                          │
│                                                             │
│  🛠 代码工匠        🔍 审查大师        📝 文档专家           │
│  "擅长生成高质量    "严格的代码审查    "需求文档和           │
│   前端/全栈代码"    专家，关注最佳     技术文档撰写"         │
│                    实践和安全性"                             │
│                                                             │
│  用户操作：@代码工匠 帮我写个登录页                           │
│  用户操作：@审查大师 检查一下代码质量                         │
└──────────────────────┬──────────────────────────────────────┘
                       │ 绑定关系（管理员/设置中配置，用户不感知）
┌──────────────────────▼──────────────────────────────────────┐
│  底层执行的（Platform 实例）                                   │
│                                                             │
│  代码工匠 → OpenCode 实例 (DeepSeek 模型后端)                 │
│  审查大师 → Codex 实例 (OpenAI 模型 / DeepSeek fallback)      │
│  文档专家 → OpenCode 实例 (DeepSeek 模型后端, 文档模式指令)    │
│                                                             │
│  每次调用时从对应平台新建会话实例                              │
└─────────────────────────────────────────────────────────────┘
```

**用户完全不需要知道：**
- 什么是 OpenCode、Codex
- 底层调用了哪个 API
- Agent 实例是怎么管理的

**用户只需要知道：**
- 这个 Agent 叫什么名字
- 它擅长做什么
- @ 它就能让它工作

## 五、Orchestrator 与上下文管理设计

> 这是本项目的**核心技术亮点**——Orchestrator 如何调度子 Agent、如何智能分配上下文，使子 Agent 既不被淹没又能获取足够信息。

### 5.1 Orchestrator 架构

```
┌─────────────────────────────────────────────────────────────────┐
│                    Orchestrator 服务                              │
│                                                                 │
│  ┌───────────────┐  ┌───────────────┐  ┌────────────────────┐  │
│  │  信息收集层    │  │   LLM 决策层   │  │    执行分派层       │  │
│  │  (Python代码) │  │ (DeepSeek API) │  │    (Python代码)    │  │
│  │               │  │               │  │                    │  │
│  │ · 读取项目结构 │  │ · 意图分析    │  │ · 调用子Agent      │  │
│  │ · 扫描文件变更 │→ │ · 任务拆解    │→ │ · 传递上下文       │  │
│  │ · 获取git状态  │  │ · Agent选择   │  │ · 监控执行状态     │  │
│  │ · 读取关键文件 │  │ · 上下文筛选  │  │ · 结果聚合         │  │
│  │ · 聊天历史摘要 │  │ · 优先级排序  │  │ · 冲突检测         │  │
│  └───────────────┘  └───────────────┘  └────────────────────┘  │
│                                                                 │
│  设计原则：                                                       │
│  · Python 负责"看"（信息收集）— 快速、确定性                       │
│  · LLM 负责"想"（分析决策）— 理解意图、规划方案                    │
│  · Python 负责"做"（执行分派）— 可靠、可控                         │
└─────────────────────────────────────────────────────────────────┘
```

**Orchestrator 不是 Agent，它是"调度员 + 信息管家"。**

- 不使用 OpenCode/Codex 实例，而是直接调用 DeepSeek LLM API
- Python 代码主动收集项目状态信息，作为 LLM 决策的输入
- 兼顾速度（单次 API 调用）和决策质量（有项目实际状态辅助）

### 5.2 上下文分层模型（Context Layering）

每次向子 Agent 分派任务时，构建四层结构化上下文：

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  Layer 0: Agent 基础指令（固定，随 Agent 配置）               │
│  ─────────────────────────────────────────────────          │
│  "你是一个全栈开发专家，使用 React + Tailwind 技术栈。        │
│   你直接在项目目录中创建和修改文件。输出时说明你做了什么。"     │
│                                                             │
│  Layer 1: 项目全局状态（共享，Orchestrator 自动维护）          │
│  ─────────────────────────────────────────────────          │
│  "【项目摘要】Todo App，React + Tailwind                     │
│   【文件结构】src/App.jsx, src/components/TodoList.jsx...    │
│   【关键决策】使用 localStorage 存储数据，不用后端             │
│   【用户偏好】按钮圆角蓝色，整体简洁现代风格                   │
│   【当前进度】已完成登录页和Todo列表，待做删除功能"            │
│                                                             │
│  Layer 2: 任务相关上下文（动态筛选，按相关性选择）             │
│  ─────────────────────────────────────────────────          │
│  "【相关文件内容】TodoList.jsx 当前代码（全文）               │
│   【最近相关对话】                                           │
│     用户: 列表项要支持勾选完成                                │
│     Agent: 已添加 checkbox 组件...                           │
│   【上次修改的 Diff】TodoList.jsx +15 -3"                    │
│                                                             │
│  Layer 3: 当前任务指令（用户本次请求）                         │
│  ─────────────────────────────────────────────────          │
│  "为每个 Todo 项添加一个删除按钮，点击后移除该项"             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 Project State Document（项目状态文档）

Orchestrator 自动维护一份「项目状态文档」，每次 Agent 完成任务后更新：

```python
# 项目状态文档结构
project_state = {
    # 基础信息
    "name": "todo-app",
    "tech_stack": ["React", "Tailwind CSS", "localStorage"],
    
    # 文件结构（自动扫描）
    "file_tree": [
        "src/App.jsx",
        "src/components/TodoList.jsx",
        "src/components/TodoItem.jsx",
        "public/index.html",
        "package.json"
    ],
    
    # 关键决策（LLM 从对话历史中提取）
    "decisions": [
        "数据存储使用 localStorage",
        "UI 风格：圆角蓝色按钮，现代简洁",
        "不使用后端 API"
    ],
    
    # 用户偏好（累积记录）
    "preferences": [
        "按钮样式：圆角、蓝色、hover 有阴影",
        "代码规范：使用函数组件 + Hooks"
    ],
    
    # 当前进度
    "progress": "已完成登录页和 Todo 列表基础功能，待添加删除和编辑功能",
    
    # 最近变更摘要
    "recent_changes": [
        {"file": "TodoList.jsx", "summary": "添加了 checkbox 完成标记", "agent": "OpenCode"},
        {"file": "App.jsx", "summary": "集成 TodoList 组件", "agent": "OpenCode"}
    ]
}
```

**更新时机：**
- 每次 Agent 完成任务后，用 LLM 总结本次变更并更新 Project State
- 文件结构在每次任务前通过 Python 自动扫描刷新
- 关键决策和用户偏好由 LLM 从对话历史中累积提取

### 5.4 上下文预算控制

```
子 Agent 的上下文窗口（假设 128K tokens）
├── Layer 0: ~500 tokens（固定）
├── Layer 1: ~2000 tokens（项目状态摘要）
├── Layer 2: 动态分配，不超过 60% 上下文窗口
│     ├── 必选：当前任务直接涉及的文件（全文）
│     ├── 应选：最近 3 轮相关对话
│     └── 可选：其他相关文件（按相关性评分截断）
└── Layer 3: ~200 tokens（当前指令）

如果 Layer 2 内容超出预算：
  → Orchestrator 调用 LLM 对长文件进行摘要
  → 或只传递文件中与当前任务相关的片段
```

### 5.5 子 Agent 会话策略（混合模式）

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  场景判断                         会话策略                     │
│  ─────────                       ────────                    │
│                                                              │
│  同一会话 + 同一Agent               → 保持 Agent Session      │
│  + 上一条也是它回复的                  （Agent 自带多轮记忆）   │
│  例："把刚才的按钮改成红色"              不重复传递已知上下文     │
│                                                              │
│  同一会话 + 同一Agent               → 部分刷新               │
│  + 但中间插入了其他Agent的回复         传递其他Agent的变更摘要   │
│  例："之前Codex建议的修改，你来实现"    + 当前文件最新状态       │
│                                                              │
│  新任务 / 切换Agent                 → Fresh Dispatch          │
```

### 5.8 Team Protocol：Agent 间协作机制（创新亮点）

> **核心理念：** Agent 之间不是互相隔离的"外包"，而是一个有共享认知的"团队"。每个 Agent 知道队友的存在、能力和决策，从而产生更高质量、更一致的协作产出。

#### 5.8.1 设计动机

```
传统多Agent（外包模型）：
  Agent A 写代码 → 提交
  Agent B 审查代码 → 不知道 A 为什么这么写 → 给出不合理建议
  Agent A 再修改 → 不知道 B 的审查偏好 → 又踩同样的坑

AgentHub Team Protocol（团队模型）：
  Agent A 写代码 → 同时声明设计决策 → "我选择 localStorage 因为..."
  Agent B 审查代码 → 看到 A 的决策理由 → 给出有针对性的建议
  Agent A 再修改 → 看到 B 的偏好和标准 → 直接对齐规范
```

#### 5.8.2 Team Protocol 三层设计

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  Layer 1: Team Board（共享看板）— P0                          │
│  ─────────────────────────────────                           │
│  · 所有 Agent 共享的项目状态、决策记录、代码规范               │
│  · 每个 Agent 工作前读取，完成后自动更新                       │
│  · 确保所有 Agent 对项目有一致理解                             │
│                                                              │
│  Layer 2: Agent Notes（便签通信）— P1                         │
│  ──────────────────────────────                              │
│  · Agent 完成任务后留"便签"给其他 Agent                       │
│  · 内容：设计决策理由、注意事项、建议、待确认问题              │
│  · 目标 Agent 下次工作时会收到并参考                          │
│                                                              │
│  Layer 3: Agent Discussion（实时讨论）— P2                    │
│  ────────────────────────────────────                        │
│  · 检测到冲突时，触发 Agent 间多轮对话                        │
│  · Orchestrator 做仲裁者，限制讨论轮数                        │
│  · 达成共识后再提交最终结果                                    │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 5.8.3 Team Board 结构

```python
team_board = {
    # 团队成员认知（让每个 Agent 知道队友）
    "team_members": [
        {"name": "OpenCode", "role": "全栈开发", "strengths": "代码生成、项目搭建"},
        {"name": "Codex", "role": "代码审查", "strengths": "质量把控、最佳实践"}
    ],
    
    # 团队决策记录（所有 Agent 共同遵守）
    "team_decisions": [
        {"decision": "使用 React 函数组件 + Hooks", "made_by": "OpenCode", "reason": "项目简单无需 class"},
        {"decision": "CSS 使用 Tailwind utility", "made_by": "OpenCode", "agreed_by": "Codex"},
        {"decision": "所有组件需要 PropTypes", "made_by": "Codex", "reason": "类型安全"}
    ],
    
    # 代码规范（由审查 Agent 主要维护）
    "code_standards": {
        "naming": "组件 PascalCase，函数 camelCase，文件名与组件同名",
        "structure": "每个组件不超过 150 行，超过则拆分",
        "style": "Tailwind utility class，避免 inline style"
    },
    
    # 当前进度（所有 Agent 可见）
    "progress": {
        "completed": ["登录页", "路由配置"],
        "in_progress": {"agent": "OpenCode", "task": "Todo列表组件"},

    ]

```

#### 5.8.4 Agent Notes 机制

```
Agent 输出格式（在原有输出基础上增加 team_note 字段）：

  "files_changed": ["src/components/TodoList.jsx"],
```

#### 5.8.6 Team Protocol 对输出质量的提升

| 场景 | 无 Team Protocol | 有 Team Protocol |
|------|-----------------|-----------------|
| 代码风格一致性 | Agent 各写各的风格 | 共享 code_standards，风格统一 |
| 重复建议 | 审查 Agent 反复提同样的问题 | 一次决策写入 Board，不再重复 |
| 设计决策冲突 | Agent A 用方案1，B 建议方案2 | A 声明理由，B 尊重或有理反驳 |
| 上下文丢失 | 新一轮修改时 Agent 忘了之前约定 | Team Board 持续记录约定 |
| 协作效率 | 来回修改多轮 | Agent 主动对齐，减少无效迭代 |

## 九、交互细节设计

### 8.1 消息流交互

| 交互场景 | 交互细节 |
|---------|---------|
| Agent 正在回复 | 消息气泡内显示打字指示器（三个跳动的点），同时消息文本流式逐字显示 |
| 流式回复中 | 底部出现"Agent 正在输入..."状态条，用户可点击"停止生成" |
| 代码块识别 | Agent 回复中的 ```code``` 自动渲染为代码卡片组件，而非纯文本 |
| 产物卡片生成 | 代码生成完成后，自动追加网页预览卡片（带 0.3s 淡入动画） |
| 发送消息 | 消息从底部滑入（150ms ease-out），自动滚动到最新消息 |
| 长消息折叠 | 超过 20 行的文本消息默认折叠，显示"展开全部" |

### 8.2 产物卡片交互

| 卡片类型 | 聊天流内展示 | 点击行为 |
|---------|------------|---------|
| 代码卡片 | 显示文件名 + 前 5 行代码预览 + 行数 | 点击 → 右栏打开完整代码编辑器 |
| 网页预览卡片 | 200px 高度缩略图（iframe 缩放） | 点击 → 右栏展开完整预览 |
| Diff 卡片 | 显示"N 行新增，M 行删除"摘要 + 前 3 行 Diff | 点击 → 右栏打开完整 Diff 视图 |

### 8.3 右栏预览面板交互

| 操作 | 行为 |
|------|------|
| 面板展开 | 首次点击产物卡片时，右栏从右侧滑入（300ms），宽度占 40% |
| 面板关闭 | 点击关闭按钮或无活跃产物时，右栏收起 |
| Tab 切换 | 预览/代码/Diff 三个 Tab 切换，保持各自滚动位置 |
| 全屏预览 | 点击全屏按钮，预览区域覆盖整个中栏+右栏 |
| 拖拽调整 | 左右栏之间可拖拽分隔线调整宽度 |
| 代码编辑 | 在代码 Tab 中修改后，预览 Tab 自动热更新（无需手动刷新） |

### 8.4 加载状态设计

| 场景 | 加载态 |
|------|--------|
| 页面首次加载 | 骨架屏（Skeleton）：左栏会话列表占位 + 中栏消息占位 |
| 会话切换 | 中栏消息区显示 Spinner (< 500ms)，超时显示骨架屏 |
| Agent 调用中 | 消息流底部显示 Agent 头像 + "正在思考..." + 跳动点动画 |
| 网页预览加载 | iframe 区域显示加载进度条，加载完成后淡入 |
| Agent 调用失败 | 红色错误提示气泡 + [重试] 按钮 |

### 8.5 空状态设计

| 场景 | 空状态内容 |
|------|-----------|
| 无会话 | 插图 + "还没有对话，点击下方按钮开始与 Agent 交流吧" + [新建对话] 按钮 |
| 新对话无消息 | 显示当前 Agent 介绍卡 + 3 个快捷提问建议（如"帮我生成一个登录页"） |
| 右栏无预览 | 浅色提示"点击聊天中的产物卡片，在此预览" |
| 搜索无结果 | "未找到相关会话" |

### 8.6 快捷操作

| 操作 | 触发方式 | 行为 |
|------|---------|------|
| @ 提及 | 输入框键入 `@` | 弹出 Agent 选择浮层，键盘上下选择，回车确认 |
| 复制代码 | 悬停代码卡片 | 右上角出现"复制"图标按钮 |
| 重新生成 | 悬停 Agent 消息 | 出现"🔄 重新生成"按钮 |
| 引用回复 | 悬停任意消息 | 出现"↩ 引用"按钮，点击后输入框上方显示引用预览 |

### 9.3 产物生成与预览数据流（基于文件变更）

```
Agent 在项目目录中工作（文件创建/修改/删除）
      │
      ▼
File Watcher 监控项目目录变更
      │
      ├── 检测到新文件创建 (如 login.html)
      │         │
      │         ▼
      │    读取文件内容 → 生成 Artifact (type: "code")
      │         │
      │         └── 如果是 HTML/CSS/JS → 额外生成 preview_url
      │
      ├── 检测到文件修改
      │         │
      │         ▼
      │    与上一版本 diff → 生成 Artifact (type: "diff")
      │         │
      │         └── 计算 hunks, additions, deletions
      │
      ▼
生成产物消息，推送给前端：
{
  message: { role: "system", content: "文件变更检测" },
  artifacts: [
    { type: "code", files: [{name: "login.html", content: "..."}] },
    { type: "diff", hunks: [...], stats: {add: 32, del: 0} },
    { type: "webpage", preview_url: "http://localhost:3001/preview/session-xxx/" }
  ]
}
      │
      ▼
前端渲染：
  - 聊天流内嵌入产物卡片缩略图
  - 点击网页预览卡片 → 右栏 iframe 加载 preview_url
  - preview_url 指向后端 Preview 服务托管的静态文件
```

### 9.4 预览服务工作原理

```
Agent 生成 HTML/CSS/JS 文件到项目目录
      │
      ▼
Preview 服务 (FastAPI 静态文件路由)
      │
      ├── 为每个会话创建预览路由: /preview/{session_id}/
      ├── 映射到用户项目目录中的文件
      ├── 支持热更新：文件变更后自动刷新 iframe
      │
      ▼
前端 iframe 加载: http://localhost:8000/preview/{session_id}/index.html
      │
      ├── sandbox="allow-scripts allow-same-origin" (安全隔离)
      └── 支持 CSS/JS/图片等资源相对路径引用
```

### 核心数据流特点

1. **Agent 是真实进程**：不是 LLM API + Prompt，而是运行中的 CLI 进程（OpenCode / Codex）
2. **文件变更驱动产物**：Agent 直接操作用户项目目录中的文件，平台通过 File Watcher 捕获变更生成 Diff
3. **流式输出透传**：Agent CLI 的 stdout 流式输出通过 WebSocket 实时推送给前端
4. **工作目录隔离**：每个会话绑定用户指定的项目目录，Agent 在其中工作

## 十六、风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| **OpenCode/Codex CLI 无法编程接入** | **核心路径受阻** | **三级降级：CLI → LLM 直调(DeepSeek API) → MockAdapter。产品闭环不受影响，评委看到的体验一致。** |
| Agent CLI 输出格式解析困难 | 无法正确提取产物 | 降级到 LLM Provider 模式（后端解析 LLM 输出写入文件） |
| DeepSeek API 调用失败或额度异常 | Orchestrator 和 LLM Provider 无模型 | MockAdapter 兜底全流程；保留 OpenAI 兼容配置，可临时切换其他兼容 API |
| 私人 API Key 成本 | 调试和端到端测试产生费用 | 设置 max_tokens、超时和预算记录；开发期优先 Mock，关键链路再调用 DeepSeek |
| 网页预览安全性问题 | iframe 执行恶意代码 | sandbox 属性 + CSP 策略限制 |
| 前期只有组长一人 | 进度压力大 | Mock-first 策略保证第 4 天即可 Demo 核心流程 |
| 20 天时间紧张 | 功能砍不完 | 严格按 P0→P1→P2 推进，P2 果断放弃 |
| Agent 进程占用资源多 | 本机性能压力 | 及时释放空闲进程，设置进程数上限 |

### DeepSeek API 成本估算（比赛 MVP）

本项目将 DeepSeek 作为比赛期间的默认 LLM 后端，用于 Orchestrator 决策和 LLMProvider fallback；它不替代 OpenCode / Codex 这两个 Agent 平台。按 DeepSeek 官方价格页（https://api-docs.deepseek.com/quick_start/pricing）在 2026-05-28 查询到的 `deepseek-v4-flash` 价格估算：cache miss 输入约 `$0.14 / 1M tokens`，cache hit 输入约 `$0.0028 / 1M tokens`，输出约 `$0.28 / 1M tokens`。价格可能变化，赛前和答辩前需复核官方页面。

| 使用阶段 | 估算输入 | 估算输出 | 估算费用 | 说明 |
|---|---:|---:|---:|---|
| 轻量调试 | 5M tokens | 1M tokens | 约 `$0.98` | 单模块联调、少量手动测试 |
| 正常开发 + 调试 | 20M tokens | 5M tokens | 约 `$4.20` | M3-M5 主要开发期 |
| 较频繁端到端测试 | 50M tokens | 15M tokens | 约 `$11.20` | 多轮 Demo 场景排练 |
| 重度测试上限 | 100M tokens | 30M tokens | 约 `$22.40` | 远超常规比赛 MVP 需求 |

预算结论：DeepSeek v4 flash 对本项目不是大开销，主要风险是误调用、循环调用或泄露 Key。控制策略：开发期默认 Mock-first；真实 LLM 调用只用于关键链路；后端限制 `max_tokens`、超时和重试次数；记录 token usage 与估算费用；`.env` 中的 `DEEPSEEK_API_KEY` 不进入仓库、不暴露给前端。
